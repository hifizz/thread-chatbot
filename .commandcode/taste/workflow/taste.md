# Workflow / Process

- 使用 OpenSpec 时，先完成并确认 `spec.md` 和 `design.md`，经用户明确同意后才编写 `tasks.md`。Confidence: 0.95
- 使用 Research/调研流程时按 Phase A/B/C/D 分阶段推进，并在每个阶段结束等待用户确认。Confidence: 0.9
- Design 文档优先定义数据契约与类型，包括新实体的数据库 schema 及输入框/表单类型，再展开其他设计内容。Confidence: 0.9
- Uses OpenSpec for change management: formalize a design as a change (`pnpm exec openspec new change "<name>"`), write artifacts in the tool's prescribed build order (proposal → specs delta → design → tasks), fetching per-artifact instructions via `openspec instructions <artifact> --change ...`, and finish with `openspec validate --all --strict`. Confidence: 0.85
- Wants change artifacts (design/tasks) grounded in verified code reality before being written — e.g. confirmed `theme.ts` dynamically builds `var(--d${N})`, enumerated every `.md-body` selector dependency in TS/CSS — rather than resting on discussion-level assumptions. Confidence: 0.75
- Operates as a principles-then-review loop: before implementation, wants a concrete and sufficiently complete plan covering responsibilities, boundaries, file structure, request flow, implementation order, and explicit non-goals; states a few inviolable principles up front, delegates the remaining design judgment ("其他的你再看看"), and wants reviewable increments presented for explicit confirmation before proceeding. This applies during implementation too: start with one focused, well-commented, standalone example file that does not yet alter the existing business path; include concrete examples for the relevant implementation variants so he can compare them, then wait for feedback rather than expanding or integrating the change unbidden. Confidence: 0.95
- When confirming a design before apply, wants concrete end-state previews — the finished module's form factor, the planned directory/file structure (e.g. the `tokens/` tree), and sample code — not prose summaries alone ("可以先把 tokens 的结构给我看吗"). Confidence: 0.7
- When a batch of edits lands on the same artifact in parallel, don't trust the per-edit result snapshots (they can show stale/inconsistent state) — re-verify the file's final on-disk state (grep for each inserted marker/phrase, spot-read the long lines) before running validation or reporting completion; caught this twice (design.md, tasks.md) and corrected course. Confidence: 0.65
- For architecture/design decisions, wants an ablation pass before the recommendation: remove abstractions that do not change required behavior and retain only the smallest core needed; specifically, verify that an abstraction is necessary before extracting a helper, module, or hook. Confidence: 0.95
- At MVP / fast-demo stage, prioritizes getting the end-to-end behavior working quickly over completeness or polish; accepts an intentionally non-perfect implementation that fits the immediate test target, and does not require backward compatibility when there are no users. Confidence: 0.95
- Treats provider routing, preferences, and settings as private implementation details that must not be exposed through public/client-facing configuration or APIs. Confidence: 0.9
- When replacing or restoring a provider integration, requires complete debranding: legacy provider names must not remain in source code or environment variables; use neutral route identifiers and renamed configuration keys instead. Confidence: 0.95
- Prefers simple, declarative, provider-local model registration with one source of truth rather than runtime model discovery: each provider owns a client-safe model metadata module that both frontend and server import; it declares only per-model differences (ID, display name, UI-relevant capabilities), while shared provider/group data is filled by a `defineProviderModels`/`createModels`-style factory. Keep API key, base URL, and SDK creation in server-only provider configuration. Adding a provider should be a localized file-level change, and `client-model.ts` / `model.ts` must not separately duplicate model or routing metadata. Confidence: 0.95
- Prefers related LLM routing and provider modules to be aggregated under a dedicated domain directory such as `lib/ai/llm/`, with a deliberately flat, readable structure rather than scattering them across the parent directory or prematurely adding nested abstraction folders. Confidence: 0.9
- Prefers using Ego Browser for real end-to-end UI smoke tests of implemented flows, including selecting a configured model and verifying request, streaming, and terminal UI behavior. Confidence: 0.75
- When implementation is ready for handoff, wants actionable acceptance guidance: a concise, prioritized set of manual test cases with steps and expected results, rather than only an implementation-complete report. Confidence: 0.7
- When validating LLM generation settings, is careful about the strength of the evidence: distinguish “the application logged/passed the parameter,” “the relay received it,” and “the upstream model actually honored it,” and do not treat a non-truncated successful generation as proof that an effort/reasoning setting took effect. Prefer controlled comparisons and observable metrics when stronger proof is needed. Confidence: 0.9
- For providers that expose a unified interface, prefers one shared API key and no artificial OpenAI-vs-Claude credential or protocol grouping; model-family distinctions should not be retained unless the provider actually requires them. Confidence: 0.95
- Uses the Git index as a review boundary: stages an existing broad rewrite first, then expects a subsequent narrow change to be inspected separately by distinguishing cached and working-tree diffs. Confidence: 0.75
- For project handoffs or status recaps, prefers a concise, directly reusable structure: requirements/background, completed work, and remaining work. Confidence: 0.95
- When a small PR is one phase of a longer-term plan, create a long-lived tracking Issue and link the PR as a milestone/phase without letting that PR close the overall Issue. Confidence: 0.95
- Allows repository-level `.commandcode` configuration and Taste preference files to be committed to Git. Confidence: 0.95
- After an implementation is accepted, complete the delivery loop by committing, pushing, and synchronizing both the PR description and the tracking Issue. Confidence: 0.95
- Even when optimizing for a quick submission, finish the remaining automated test suite before declaring the change ready to commit. Confidence: 0.8
- Avoids crowded catch-all directories: when a domain accumulates multiple related files, move them into a dedicated subdirectory. If a directory migration is warranted, complete all file moves and reference updates atomically rather than leaving a partial migration for later. Confidence: 0.95
