# ThreadChat 继承上下文压缩调研报告

> 调研日期：2026-07-30。范围：`app/thread-chat/` 分支会话页的上下文装配链路（`buildRequestBody` → `/api/chat`），目标是**降低每个叶子节点（分支会话）的单轮成本，同时不丢关键信息**。
> 报告里的所有数字来自 `scripts/context-cost-sim.mjs`——它直接 import 线上真实函数（`collectInherited` / `serializeMessageForModel` / `applyInheritedBudget` / 真实 system 常量），在合成会话树上重放请求，改代码后可重跑复现。

---

## 0. 摘要（TL;DR）

1. **先纠正一个直觉：现在的账单不是被"继承上文"撑爆的，输出侧才是大头。** 在典型浅树场景（主线 6 轮 + 7 个分支）里，输入成本只占 33%，输出占 67%；深用场景也只有 39% / 61%。把回答平均长度从 1800 字压到 1000 字，总成本直接降 37%——比任何输入侧压缩都猛。当前 system 明确写着「不必刻意压缩篇幅」（`constants/thread-chat.ts:9`），这是自选的成本结构，不是意外。
2. **输入侧最大的单一变量不是"塞多少字"，而是"前缀缓存命不命中"。** 同一份现状算法，全命中与全不命中的账单差 25%（浅树 ¥2.10 vs ¥2.79）到 42%（深用 ¥5.55 vs ¥9.54）。方舟隐式缓存命中价约为正常输入价的 2 折、DeepSeek 低至 2%——**这是唯一"零信息损失还省钱"的杠杆**，应该排在所有摘要方案前面。
3. **而现状的三处设计正在系统性地砸掉缓存命中**：① 分支锚点原文被拼进 system（`lib/chat/thread-chat-prompt.ts:19`），使每个分支从第 ~450 token 起前缀就分叉；② 继承段预算「从最新往回收、丢最旧」并在**最前面**插一条「（更早的 N 条上文已省略）」，让兄弟分支的前缀从第一条消息就不同；③ 方舟缓存块最小 1024 token，而通用 system（447 tok）单独不够一块。
4. **"丢最旧"这个截断方向本身还有信息损失问题**：一棵树里最该保住的是主线开场那几轮（题目是什么、约束是什么），而现算法优先丢的正是它们，留下的是靠近 fork 点的中段闲聊。深树上"根问题丢失"是可预期的失真。
5. **当前会话（本分支自己的消息）完全没有预算**，随轮次 O(n²) 累积：主线第 10 轮单请求 11.6k token、第 20 轮 24k token，累计 24.5 万 token。分支通常短（2–4 轮）所以现在不痛，但这是唯一无上界的一段。
6. **朴素的"每轮现场重算摘要"是负收益，且幅度惊人**：模拟显示原始输入 token 降 44–57%，但账单反而涨 76%（浅树 ¥3.71 vs ¥2.10）到 120%（深用 ¥12.18 vs ¥5.55）——因为摘要调用每轮都要把历史再读一遍（付第二遍输入费），同时把缓存命中率打到 0–1%。**这是本报告最重要的一条警告：上下文压缩做错方向，比不做贵一倍。**
7. **推荐的算法是「确定性分段封存」（Deterministic Sealed Compaction）**：祖先链按**消息序号**切成固定块，块边界不随轮次移动；旧块用一次性生成、写进树状态的摘要替代，所有后代与后续轮次复用**同一份字节**。这样压缩既是"每块只付一次"，又天生保持前缀稳定——**会话树的结构本来就同构于前缀缓存的 trie，只要序列化保证"祖先在前、逐字节确定"，整棵树天然共享 KV 前缀**。
8. **它的定位要说清楚：不是"比现状更省钱"，而是"用相近的钱换回被丢掉的信息"。** 模拟里 D 方案（分段封存 + Artifact 引用化）相对现状：原始输入 -7%（浅树）/ -4%（深用），账单 +4%（浅树）/ +1%（深用），但祖先链从"只剩最近 6000 字"变成"全覆盖（远端摘要 + 近端原文）"。真正的省钱来自第 2、9 条。
9. **Artifact 全文重放是个明确可摘的果子**：现状每轮把消息挂的 Markdown 全文原样回放（`message-serialization.ts:17`）。改成"最近一份留全文、更早的降级为标题 + 大纲 + `readArtifact` 按需取回"，输入 token -7%，且不影响"改一下刚才那份文档"的能力。
10. **在动手之前先补观测**：`usage_records` 现在既不记 `treeId/threadId/depth`（thread-chat 请求体根本没带 `id`），也不采集缓存命中 token（AI SDK v7 已经在 `usage.inputTokenDetails.cacheReadTokens` 给出、`@ai-sdk/openai-compatible` 已映射 `prompt_tokens_details.cached_tokens`）。**现在无法回答"一个叶子节点到底花了多少钱"，也无法验证任何优化是否生效**——这是 P0 的第一步。

## 1. 现状：一次分支请求到底由什么组成

### 1.1 装配链路（代码级）

```
core/store（整棵 ThreadTreeState）
  └─ net/prompt.ts:65  buildRequestBody(state, thread, excludeMsgId)
       ├─ core/selectors.ts:47  collectInherited      沿 lineage 逐层截到 forkFromMsgId
       ├─ net/message-serialization.ts:7  serializeMessageForModel   正文 + quote 前缀 + Artifact 全文
       ├─ net/prompt-pure.ts:27  applyInheritedBudget  6000 字预算，从最新往回收
       └─ 输出 { messages, modelId, threadChat:{ anchorText } }
            └─ app/api/chat/route.ts:182  buildThreadChatSystem(anchorText)   ← system 服务端构造
                 └─ streamText({ system, messages, tools:{createMarkdownArtifact}, stopWhen: isStepCount(5) })
```

### 1.2 三段结构与实测规模

| 段 | 内容 | 规模（默认参数下） | 是否有上界 |
|---|---|---|---|
| 固定头 | 通用 system（`THREAD_CHAT_SYSTEM`，671 字 ≈ 447 tok）+ 分支焦点段（133 字）+ `createMarkdownArtifact` 工具定义与 schema（描述 ~800 字） | ≈ 1000–1100 tok / 每次请求 | 是（常量） |
| 继承段 | 祖先链每层截到 fork 点的全部消息 | ≤ 6000 字 ≈ 4000 tok | 是（`INHERITED_CHAR_BUDGET`） |
| 本会话段 | 当前分支已有的全部消息（含 Artifact 全文） | **无上界**，随轮次线性增长 | **否** |

模拟中「现状」策略的分段占比（浅树场景，27 次请求合计 138,929 输入 tok）：system 段 14,139 tok（10%）、继承段 63,488 tok（46%）、本会话 61,179 tok（44%）。深用场景（91 次请求）本会话段占到 67%。
（模拟只统计 system + 消息，**未计入工具定义**——`createMarkdownArtifact` 的描述与 JSON schema 每次请求都要随 `tools` 一起发出，实际固定头还要再加约 500 tok/请求。这部分是纯常量，正是最该被缓存吃掉的一块。）

### 1.3 现有的唯一压缩手段

只有 `applyInheritedBudget`（`prompt-pure.ts:27`）：从最新一条往回累加正文字符，超过 6000 字就停，更旧的整条丢弃（保底留 1 条），并在继承段最前插一条 `（更早的 N 条上文已省略）`。除此之外没有摘要、没有窗口、没有检索、没有 Artifact 降级、没有缓存工程。

## 2. 瓶颈定位（量化）

### 2.1 方法与口径

- 用 `scripts/context-cost-sim.mjs` 在三种会话树形态上按真实交互顺序重放全部请求。
- token 按字符折算（中文 + Markdown 混排取 1.5 字/token），**不是真实 tokenizer 结果**，±20% 内的偏差不影响结论方向。
- 价格取 `constants/pricing.ts` 里 Coding Plan 的保守内部估值 ¥10/¥40 每百万 token（输入/输出）。
- **「命中%」是理想上界**：假设前缀缓存全局共享、TTL 无限、逐字节相同即命中，并按方舟「缓存块 ≥1024 token」向下取整。真实值一定更低，所以表里同时给出「无缓存¥」作为下界——**真实账单落在这两列之间，而工程目标就是把它往「有缓存」那一侧推**。

## 3. 环节地图：上下文压缩可以在哪些地方做

| 环节 | 这一环能做什么 | 代表技术 | 本项目适配度 |
|---|---|---|---|
| **E1 固定头**（system + 工具定义） | 缩短、去重、保持逐字节不变 | 静态 prompt、工具定义常驻不变（Manus：用 logits mask 而非动态增删工具） | 高：现状 system 671 字里有大量重复的 Markdown 工具指令，可精简；但**不要**为省几百 token 破坏稳定性 |
| **E2 继承段**（跨节点，本报告核心） | 摘要 / 选择 / 检索 / 层级化 | 一次性封存摘要、RAPTOR 式层级树、检索式注入、结构化记忆 | 高：会话树天然是层级结构 |
| **E3 本会话段**（节点内） | 滑动窗口、阈值触发 compaction、递归摘要 | Anthropic compaction、LangGraph running summary、ACON/ReSum 类阈值触发 | 中：分支通常短，主线长 |
| **E4 Artifact / 附件** | 引用化 + 按需取回、分块检索 | 工具化取回（`readArtifact`）、pgvector 检索（项目已有 `lib/chat/retrieve.ts`） | 高：改动小、收益直接 |
| **E5 传输结构与顺序** | 让稳定的排前面、可变的排后面，保证前缀逐字节确定 | KV/前缀缓存工程（Manus、DeepSeek disk cache、方舟隐式缓存） | **最高**：零信息损失 |
| **E6 输出侧** | 控制篇幅、限制步数、避免复述步 | system 篇幅约束、`maxOutputTokens`、`stopWhen` | 高：成本占比最大 |
| **E7 计费与观测** | 采集缓存命中、按 tree/thread/depth 归因 | `usage.inputTokenDetails.cacheReadTokens` | 前置条件 |

## 4. 各环节的技术方案与取舍

### 4.1 E5 前缀缓存工程（无损，优先级最高）

**外部证据**

- Manus 的工程总结把 **KV-cache 命中率称为"生产级 agent 唯一最重要的指标"**，因为输入/输出 token 比常在 100:1；核心纪律是：前缀必须逐字节稳定（一个 token 的差异就让其后全部失效，典型翻车是把精确到秒的时间戳放进 system 开头）、上下文 append-only、序列化确定性。
- **DeepSeek**：磁盘上下文缓存自动生效，只有**从第 0 个 token 起完全相同的前缀**才算命中；命中价约为未命中的 1/50（V4-Flash：$0.0028 vs $0.14 每百万）。
- **火山方舟**（本项目 `THREAD_CHAT_MODELS` 的实际通道）：隐式缓存**自动开启且不可关闭**，系统自动识别公共前缀但不保证命中；**缓存块最小 1024 token** 才参与匹配；命中单价约为正常输入价的 2 折（Doubao-Seed-2.1 Pro：¥6/M → ¥1.2/M）。
  ⚠️ **待核实**：公开资料明确点名的隐式缓存支持范围是 doubao-seed-2.0 及之后系列与 seed-code；而 thread-chat 的默认模型是 `glm-5.2`，还挂着 kimi / deepseek-v4 等第三方模型（`constants/model.ts`）。**这些模型经 Coding Plan 端点是否同样享有隐式缓存、以及 usage 是否回传 `prompt_tokens_details.cached_tokens`，必须先用 P0-2 的观测实测确认**——如果第三方模型不支持，缓存工程的收益就只落在豆包系上，选型（默认模型）本身也会变成一个成本决策。
- AI SDK v7 已经把命中量透出到 `usage.inputTokenDetails.cacheReadTokens`（`node_modules/ai/dist/index.d.ts:329`），`@ai-sdk/openai-compatible` 也已映射上游的 `prompt_tokens_details.cached_tokens`——**我们只是没读它**。

**落到本项目的四条规则**

1. **稳定的排前面、可变的排后面**：`[通用 system + 工具定义][祖先上下文（自根向下）][分支焦点段][本分支消息][本轮提问]`。焦点段从 system 移到继承段之后，是把"每个分支各不相同的那 133 字"从前缀里挪走。
2. **祖先序列化必须是前缀单调的**：子节点的上下文 = 父节点上下文 + 父节点新增消息。今天的"丢最旧"截断恰好破坏这一点（同一父的两个 fork 点不同的兄弟，会得到两段开头就不同的文本）。**保头去尾天然保持前缀性质，保尾去头不保持**——这正是推荐算法要"从旧到新按块封存"而不是"整体截断"的根本原因。
3. **任何压缩产物必须固化**：同一个块的摘要必须字节相同地被所有后代、所有轮次复用（写进 `ThreadTreeState`，随整树 JSON 落库），绝不能每次请求现算。
4. **别让不确定性混进前缀**：时间戳、随机 id、`Object.keys` 顺序、`Date.now()`。现状在这点上是干净的（消息 id 不进模型正文，`convertToModelMessages` 只保留 role/content）。

**会话树 = 缓存 trie**：把树的每条根到叶路径按上述规则序列化，兄弟分支自动共享到 fork 点为止的全部前缀，深分支自动共享祖先前缀。这是这个产品形态**独有的红利**，现状没吃到。

### 4.2 E2 继承段压缩：五类方法

| 类别 | 做法 | 优点 | 缺点 / 本项目判断 |
|---|---|---|---|
| **① 截断（现状）** | 丢最旧、保最近 6000 字 | 零成本、零延迟、可预测 | 丢主线开场（最该保的）；破坏前缀；深树失真 |
| **② 一次性封存摘要（推荐）** | 按序号切块，旧块生成一次摘要并固化 | 每块只付一次，跨后代/跨轮次摊薄；前缀稳定；可后台异步 | 有一次性生成成本与延迟；摘要质量需评测把关 |
| **③ 滚动重算摘要（反模式）** | 每轮把历史重新总结 | 实现最简单 | **模拟实测账单 +76%~+120%**，命中率归零。绝不采用 |
| **④ 检索式（RAG over 会话树）** | 把祖先消息切块建索引，按当前问题取 top-k | 长树下 token 最省；项目已有 pgvector（`lib/db/schema.ts` 的 `attachment_chunks` + `lib/chat/retrieve.ts` + `lib/ai/embeddings.ts`） | 命中内容每轮都变 → **必须注入在稳定前缀之后**（焦点段之后、当前消息之前）才不破坏缓存；需要 embeddings 供应商配置；一期不必上 |
| **⑤ 结构化记忆** | 抽事实/实体进外部 memory（Mem0、Zep/Graphiti、Letta/MemGPT） | LOCOMO 上 Mem0 报告 token −90%（1.8k vs 26k）、p95 延迟 −91% | 面向"跨会话长期记忆"，而我们要的是"一棵树内部的上下文继承"；引入新服务与新失败面，收益错配。**作为 P2 观察项**，不进本轮 |

**关于摘要成本的直觉纠偏**：一份摘要的成本 = 读一遍原文（输入）+ 写摘要（输出）。方案②里它被"块数"上界住，且被所有后代分摊；方案③里它是"每次请求 × 全部历史"，本质是**把历史又买了一遍**。模拟中场景二 X 方案的摘要开销高达 554,412 tok，比它省下的输入还多一倍。

**并行分块 compaction 的外部佐证**：arXiv:2605.23296《Parallel Context Compaction for Long-Horizon LLM Agent Serving》指出串行 LLM 摘要慢且输出体量不可控，改为**按块并行压缩**能显著降低端到端墙钟时间并提升吞吐——与"按序号切块、块间独立、可并行/后台生成"的设计方向一致。

**层级化的天然同构**：RAPTOR（ICLR 2024）通过递归聚类 + 抽象摘要构建多层级树，在需要多跳推理的问答上把 QuALITY 绝对准确率提升 20%。ThreadChat 的会话树**本来就是人工构造好的层级结构**（每个分支自带 anchorText 作为"这一层在讲什么"的标签），不需要聚类步骤，直接在既有节点上挂摘要即可——这是比通用 RAPTOR 更省的一条路。

### 4.3 E3 本会话段

- **确定性窗口 + 块封存**（推荐）：本会话消息同样按固定序号块（如每 8 条）切，超过保留轮数的旧块封存为摘要。关键仍是**块边界由序号决定，不随轮次移动**——否则每轮边界移动一次就等于方案③。
- **阈值触发 compaction**：Anthropic 的做法是接近上下文上限时把整段对话总结后重开窗口，并强调"先最大化召回、再迭代提升精度"。适合做**兜底**（例如单请求 > 40k token 时强制 compaction），不适合做常规路径。
- 收益判断：模拟场景二里本会话封存把**单请求峰值从 19,273 tok 压到 12,162 tok（−37%）**，但账单略升（¥5.90 vs ¥5.55）。所以它的正确定位是**延迟 / TPM 限流 / 上下文腐烂（context rot）治理**，不是省钱手段。

### 4.4 E4 Artifact 与外部资料

- **引用化 + 按需取回**：非最近的 Artifact 只放 `[Markdown Artifact: 标题｜N 字，正文按需取回]` + 大纲（ATX 标题列表），配一个 `readArtifact(id)` 后端工具。模拟 −7% 输入 tok，且"改一下刚才那份文档"仍然成立（最近一份保留全文）。
- **与 B8 联动**：Artifact 生成后的那一步（`stopWhen: isStepCount(5)`）会把刚写完的全文当输入再读一遍。若引用化规则同时作用于"同一响应内的后续步骤"，这笔钱也能省；但要保住"一次交付多份文档"的能力，需要在 `prepareStep` 里按步号区分处理。

### 4.5 E6 输出侧（成本占比最大）

- 现状 system 写着「在有价值处展开细节、举例、说明常见误区或延伸，**不必刻意压缩篇幅**」。这是产品调性，不建议粗暴改全局；但**分支的焦点段完全可以要求"聚焦、克制"**——分支本来就是"就这一句话展开讲"，不需要每次都从头铺陈。
- `MAX_OUTPUT_TOKENS = 8192`（`constants/model.ts:139`）是安全阀，不是成本控制。可考虑按模式区分（分支答复给更小的上限）。
- 敏感性（浅树场景、现状算法）：回答平均 1000 / 1800 / 2600 字 → 总成本 ¥1.33 / ¥2.10 / ¥2.81，其中输出成本 ¥0.83 / ¥1.40 / ¥1.98——**输出侧几乎线性，且它同时把输入也顶高**（历史更长 → 后续每轮输入更贵）。

### 4.6 E7 计费与观测（前置条件）

1. 请求体带上 `id`（treeId 或 `treeId:threadId`）与 depth，让 `usage_records` 能按树 / 分支 / 深度归因。
2. `onFinish` 里读 `usage.inputTokenDetails.cacheReadTokens / cacheWriteTokens`，写进 `usage_records` 与 `UsageMetadata`。
3. `constants/pricing.ts` 增加 `cachedInputPerMillion`（方舟按 2 折、DeepSeek 按 2%），`costMicros` / `priceMicros` 分开计价。**当前命中时仍按未命中价向用户收费**，既不符合"成本 + 30% 利润"的口径，也让所有压缩收益在账面上隐形。

### 4.7 明确不建议的方案

- **token 级压缩（LLMLingua-2 等）**：论文报告 2–5× 压缩（极限 14×）且在 LongBench 中文任务上优于前代，但需要引入 Python 侧 xlm-roberta 压缩模型；产出是"人读不懂的稀疏 token 串"，会破坏消息可读性（我们的消息还要在 UI 上展示、要支持划选开分支），且压缩结果不稳定 → 前缀缓存失效。收益/代价不成比例。
- **换更长上下文的模型来"不压缩"**：标称窗口 ≠ 有效窗口（Chroma 的 Context Rot 实测 18 个前沿模型性能随输入长度单调下降），且成本随长度线性上涨。
- **把整棵树的所有分支都塞进上下文**：分支隔离本来就是这个产品的价值（每个叶子只带自己那条路径），不要为了"信息全"把它毁掉。

## 5. 推荐算法：确定性分段封存（Deterministic Sealed Compaction）

**一句话**：祖先上下文按消息序号切成固定块；靠近 fork 点的近端块保留原文，远端块替换为**一次性生成并写进树状态**的块摘要；分支焦点段移到继承段之后；Artifact 在远端降级为引用。

**四条不变式**（缺一条就退化成反模式）

1. **块边界只由消息序号决定**——不随轮次、不随分支、不随预算浮动。
2. **摘要一次生成、永久固化**——存 `ThreadTreeState`，随整树 JSON 落库；同一块对所有后代字节相同。
3. **前缀单调**——子节点上下文严格以父节点上下文为前缀。
4. **降级永不阻塞对话**——摘要还没生成好就退回原文（贵一点但正确），生成失败只 `console.warn`，与 `net/branch-title.ts` 的异步标题生成同一套姿势。

**数据结构（示意）**

```ts
// core/types.ts
interface SealedBlock {
  threadId: string   // 块所属会话
  index: number      // 块序号（= 起始消息下标 / BLOCK_SIZE），块边界的唯一依据
  summary: string    // 固化摘要，生成后不可变
  srcMsgIds: string[] // 溯源：这一块覆盖了哪些消息（供 UI「展开原文」与失效判定）
  model: string      // 生成模型，便于日后重算
}
interface ThreadTreeState {
  // …existing
  seals: Record<string, SealedBlock> // key = `${threadId}#${index}`
}
```

**装配伪码**

```
buildRequestBody(state, thread):
  segments = [ 通用 system ]                       // 稳定
  for block in ancestorBlocks(state, thread):       // 自根向下，块边界 = 序号
      if block 距 fork 点 > KEEP_RECENT_BLOCKS:
          segments += seals[block.key] ?? 原文(block)  // 有摘要用摘要，没有就先用原文
      else:
          segments += 原文(block)（Artifact 全文仅限最近一份）
  segments += 分支焦点段（anchorText）               // 每分支不同 → 放在共享前缀之后
  segments += 本会话消息（超长时同样按序号块封存）
  segments += 本轮提问
```

**摘要生成时机**：分支创建后（首答完成时，复用 `POST /api/branch-title` 那条异步侧路的模式）为"新变成远端"的块补生成；块之间互不依赖，可并行。用便宜模型（`doubao-seed-2.0-lite`）。

**摘要提示词的要求**（决定信息保真度）：保留 ① 用户提出的问题与约束；② 结论与关键定义；③ 专有名词、数字、代码标识符原样；④ 未解决/待办项。明确要求不复述客套与排版。Anthropic 的经验是**先把召回拉满（宁可长），再迭代砍冗余**。

**为什么它同时满足"省"和"不丢"**：远端块被压到 ~300 字但仍在场（不像现状直接消失），近端保持原文（指代消解不受影响），摘要成本被块数上界住并跨所有后代摊薄，前缀稳定让缓存吃掉大头。

## 6. 落地路线与验收指标

### P0（先测量、先做无损项；不改任何"给模型看什么"的语义）

| 项 | 改动 | 验收 |
|---|---|---|
| P0-1 成本可归因 | 请求体带 `id`（treeId:threadId）+ depth；`chargeUsage` 落库 | 能出"每棵树 / 每个分支 / 每个深度的成本"报表 |
| P0-2 缓存可观测 | 采集 `inputTokenDetails.cacheReadTokens/cacheWriteTokens`，入 `usage_records` 与 `UsageMetadata` | 能出真实命中率曲线（对照本报告 61–81% 的上界） |
| P0-3 缓存友好重排 | 焦点段从 system 移到继承段之后；system 只留通用段 | 命中率上升；`e2e/thread-chat` 全绿 |
| P0-4 计费口径 | `pricing.ts` 增加缓存命中单价，分开计价 | 命中场景下用户账单下降，利润率仍 ≥30% |

### P1（信息保真度提升 + 真正的压缩）

| 项 | 改动 | 验收 |
|---|---|---|
| P1-1 继承段改为分块 + 保头 | 去掉"丢最旧 + 省略说明置顶"，改为按序号块、远端优先降级 | 深树里主线开场信息不再消失；前缀单调性通过单测 |
| P1-2 确定性封存摘要 | `SealedBlock` + 异步生成 + 降级 | 祖先链覆盖率 100%；单请求 token 不高于现状 +10% |
| P1-3 Artifact 引用化 + `readArtifact` | 非最近 Artifact 降级为标题 + 大纲 | 输入 −5%~−10%；"改刚才那份文档"用例仍通过 |
| P1-4 分支答复篇幅约束 | 焦点段追加"聚焦、克制"指令 | 输出 token 中位数下降，人工抽检质量不降 |

### P2（可选，按数据决定）

- 本会话段的确定性封存（面向长主线；主要收益是峰值 token 与延迟）。
- 检索式继承（复用 pgvector），注入位置严格限定在稳定前缀之后。
- 跨树的长期记忆（Mem0/Zep 类）——只有在"用户跨树复用知识"成为真需求时才评估。

## 7. 信息保真度怎么验（不做这步就没法说"没丢太多"）

1. **构造评测集**：从真实树里取 30–50 个分支，每个准备 3 类问题——① 指代类（"这段话里说的它是什么"）；② 回溯类（"我们最开始要解决的问题是什么"，专打"丢最旧"）；③ 交付类（"把刚才那份文档改成 X"，专打 Artifact 引用化）。
2. **A/B 同题**：同一问题分别用现状与新算法各生成一次。
3. **LLM-as-judge + 人工抽检**：判"是否包含正确的上文事实"，而不是判文风。
4. **门槛**：回溯类正确率必须**优于**现状（现状会丢），指代类与交付类不得下降；同时报告 token / 成本变化。

---

## 8. 风险与反模式清单

- ❌ **每轮现场重算摘要**——模拟实测账单 +76%~+120%，命中率归零。
- ❌ **让摘要边界随轮次滑动**——等价于上一条。
- ❌ **把可变内容（锚点、时间、检索结果）放在稳定前缀之前**。
- ❌ **为省几百 token 而频繁改 system**——每改一次，全量缓存作废一次。
- ⚠️ **摘要生成失败/未就绪**必须能退回原文，不能阻塞发送、不能报错。
- ⚠️ **`applyInheritedBudget` 与 `e2e/thread-chat/prompt-budget.test.mjs` 强绑定**：改算法要同步改测试期望，且新算法应补"前缀单调性"用例。
- ⚠️ **Coding Plan 是订阅制**，token 不直接等于人民币；但 `usage_records` 是向用户计费的依据，口径错了是产品问题不是成本问题。
