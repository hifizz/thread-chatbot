# Thread Chat 引用与缓存调研（产品易读版）

> **阶段：Research**  
> **面向读者：产品经理、设计者、希望系统理解缓存但不熟悉模型基础设施的人**  
> **目的：帮助判断方向是否正确。详细 DTO、数据库职责、Parts 协议和工程任务见同一 OpenSpec change。**

---

## 一、30 秒结论

我们要解决两件事：

1. 用户从一段长对话创建多个分支时，模型不应该反复重读完全相同的历史；
2. 用户从任何地方划选内容时，都应该先把引用放进输入框，允许继续追加、批注和整理，然后一次性发送。

推荐方案：

```text
固定规则
共同历史
已完成的当前分支历史
-------------------------
本轮引用 1..50
每份引用自己的批注
本轮总问题
```

核心原则：

> 相同内容放前面，变化内容放后面；模型不需要的 ID、定位信息和界面信息完全不发送。

---

## 二、缓存是什么

模型每次回答前都要读一遍输入：

```text
系统规则
工具说明
历史对话
当前问题
```

如果下一次请求的开头和上一次完全相同，模型服务商可能复用“已经读懂这段内容”的计算结果。

缓存的不是旧答案，而是：

> 模型处理相同输入前缀时已经做过的中间计算。

因此缓存可能带来：

- 更低的重复输入成本；
- 更快的回答开始速度；
- 分支越多，共同历史复用价值越大。

---

## 三、怎样才能复用缓存

最重要的条件是：

> 两次请求必须从开头开始，拥有足够长、顺序和文字都相同的一段内容。

好的结构：

```text
固定规则
A 的共同历史
B1 的引用和问题
```

另一个兄弟分支：

```text
固定规则
A 的共同历史
C1 的引用和问题
```

两次请求可以先共同走到 A 历史结束，之后才发生差异。

不好的结构：

```text
固定规则
B 的具体引用
A 的共同历史
B1
```

因为 B 和 C 的引用不同，它们在进入 A 历史以前就分叉了，后面的共同历史也难以作为一个连续相同开头复用。

---

## 四、当前代码为什么没有充分利用缓存

当前数据结构本身没有大问题：

- Thread B 保存从哪里分出来；
- `forkContext` 冻结 A 的共同历史；
- B1 保存用户问题。

真正的问题是发给模型时，具体 `anchorText` 被放进了前面的 System Prompt：

```text
System + B 的具体引用
A 的历史
B1
```

所以我们要把具体引用从 System 移走，放回 B1 用户消息：

```text
固定 System
A 的历史
B1：引用 + 问题
```

---

## 五、引用不是“发送”，而是输入草稿的一部分

这是这次补充后最重要的产品统一。

用户划选一段内容后，可以：

```text
开新分支
添加到当前 Thread 输入框
继续再选其他内容
给每段内容写批注
最后一次发送
```

在用户真正点击发送以前，这些都只是 Composer Draft：

- 不创建用户 Message；
- 不创建 AI 占位 Message；
- 不调用模型；
- 不产生 Token 成本；
- 不影响已有缓存。

---

## 六、四条用户路径其实是一套逻辑

### 1. 划选后直接输入问题开分支

```text
引用：A2 中选中的段落
问题：为什么必须是相同前缀？
```

系统直接创建 Thread B、B1 和 AI 回复。

### 2. 划选后不输入问题

用户只是想先开一个分支，还没想好怎么问。

正确行为：

```text
只创建 Thread B
打开 B
在输入框上方显示引用 Quote Block
不发送
不调用模型
```

用户之后可以继续：

- 输入问题；
- 再添加多份引用；
- 添加附件；
- 一次性发送。

### 3. 引用到当前 Thread

用户划选后不一定要开新分支，也可以选择：

```text
添加到当前输入框
```

它只把 Quote Block 加入当前 Composer，不自动发送。

### 4. Markdown 批量批注

用户对文档多段文字分别写评论：

```text
引用 1 + 评论 1
引用 2 + 评论 2
引用 3 + 评论 3
```

确认批量批注后，这些内容一起进入目标 Thread 输入框。用户检查后一次发送，只触发一次 AI 回复。

## 七、为什么一条消息要支持 50 个 Quote

之前设计最多 8 个，不够覆盖批量批注和多材料汇总。

现在确定：

```text
每条用户 Message 最多 50 个 Quote
```

但要注意：

> 50 是“块的数量上限”，不是“可以无上限发送 50 篇长文”。

所以系统还要做一次费用保护：

```text
Quote 数量检查
+ 每份长度检查
+ 当前模型的 Token 预算检查
+ 整次输入预算检查
```

如果内容太大，必须在模型调用前提示用户删减，不能：

- 静默删掉几段；
- 偷偷截断；
- 未经用户同意自动摘要；
- 先产生昂贵调用再报错。

---

## 八、什么内容可以被引用

已确认规则：

```text
只允许 completed 的 AI 回复
```

以下全部不允许：

```text
generating：还在生成
stopped：用户中途停止，内容可能不完整
failed：生成失败
```

Markdown Artifact 也必须来自一条 completed AI 回复。

这样 Quote 是稳定快照，不会把半截内容当作可靠来源。

---

## 九、Quote 中保存什么

每份 Quote 需要保存两类信息。

### 给模型看的

```text
引用正文
用户针对这一段的可选评论
```

### 给产品功能使用的

```text
来源 Project
来源 Thread
来源 Message
来源 Artifact（如果来自文档）
TextAnchor：原文位置线索
```

产品元信息用于未来：

- 点击引用跳回来源；
- 打开正确 Thread 或 Artifact；
- 滚动到原 Message；
- 重新定位并高亮原文。

这些 ID 和位置线索不需要发给模型，因此不会增加 Token，也不会破坏缓存。

## 十、为什么批注要和 Quote 保持一一对应

如果把所有评论拼成一个大文本：

```text
评论 1……
评论 2……
评论 3……
```

以后很难知道每条评论对应哪段原文。

所以每个 Quote Block 自己保存：

```text
引用正文
该段评论（可选）
来源信息
```

普通多引用问题可以没有逐条评论，只在底部写一个总问题。

批量批注则每个 Quote 都带自己的 comment，还可以再附加一段总说明。

---

## 十一、这些引用如何发给模型

模型应该看到：

```text
引用 1 正文 + 评论 1
引用 2 正文 + 评论 2
用户总问题
```

模型不应该看到：

```text
Quote ID
Thread / Message / Artifact ID
TextAnchor
标题和脚注
列位置
请求 ID 和 Trace ID
```

因此后端必须有唯一转换函数，把 Quote 内容转成稳定格式，其他地方不能各自随意拼字符串。

## 十二、怎样系统保护缓存

可以把所有输入分成四类。

### 1. 稳定前缀

尽量长期不变：

```text
工具定义
Agent 基本规则
Project 固定规则
分叉前共同历史
已经完成的当前分支历史
```

### 2. 动态尾部

每轮变化，但必须放到最后：

```text
本轮研究计划
本轮 Quote 和评论
当前问题
当前附件
```

### 3. 不发给模型的信息

```text
各种 ID
TextAnchor
标题、脚注、列位置
输入框 Draft ID
```

### 4. 主动划分新缓存空间的变化

这些变化确实代表不同计算，不能硬共享：

```text
切换模型
切换实际服务线路
工具权限变化
Agent 规则版本升级
Project 规则更新
缓存保留政策变化
```

以后增加任何 Prompt 内容，都应该先问：

1. 模型需要看到吗？
2. 多久变化一次？
3. 能不能放到最后？
4. 变化后应该局部失效，还是开一个新缓存空间？
5. 怎么证明它没有破坏缓存？

## 十三、你看不懂的“先验证哪条 Claude 路线”是什么意思

同一个 Claude 模型可能通过不同渠道调用：

```text
直接调用 Anthropic
经过 UMAPIS
经过 OpenRouter
经过 Vercel Gateway
经过私有中继
```

这些渠道不一定都支持同样的缓存功能。

当前项目里的 Claude 模型实际走 UMAPIS，所以不用你先选择：

> 第一条就验证当前真正使用的 UMAPIS Claude。

如果普通调用成功，但 UMAPIS 不返回缓存数据，就不能宣称已经命中。此时再用直接 Anthropic 做参考测试，判断问题在我们的 Prompt，还是在中转渠道。

---

## 十四、你看不懂的“5 分钟还是 1 小时”是什么意思

它只是指：

> 模型服务商愿意把已经计算过的共同前缀保留多久。

先做保守方案：

```text
默认短时缓存
支持时先验证约 5 分钟
1 小时缓存先关闭
```

原因：

- 长时缓存可能有额外写入成本；
- 可能涉及更长数据保留；
- 不一定能被后续请求充分复用。

只有真实数据证明用户经常在 5 分钟以后回来，而且节省大于成本，才单独启用 1 小时。

## 十五、最终目标请求

### 第一次进入 B

```text
稳定工具
固定 Agent 规则
Project 固定规则
A 的冻结历史
---------------- 缓存边界 ----------------
本轮运行信息
B1：Quote 1..N + comments + 总问题
```

### B 中继续下一轮

```text
稳定工具
固定 Agent 规则
Project 固定规则
A 的冻结历史
B1
BA1
---------------- 新缓存边界 ----------------
B2
```

这时既能复用 A 的共同历史，也能复用 B 已经完成的历史。

## 十六、成功标准

1. 同一 A 历史产生的兄弟分支，在当前 B1/C1 之前拥有相同前缀。
2. 空问题开分支不调用模型，Quote 正确显示在新 Thread 输入框。
3. 当前 Thread 引用和批量批注只修改 Draft，直到一次发送。
4. 一条 Message 支持最多 50 份 Quote，并在超预算时付费调用前拒绝。
5. `stopped/generating/failed` 来源不可引用。
6. 模型只看到 Quote 正文/comment，不看到来源元信息。
7. 系统能区分：理论上可复用、冷启动、部分温缓存、Provider 真正命中。
8. UMAPIS Claude 只有在真实 Usage 证明后才标记启用。
9. 首阶段只启用短时缓存。
10. 缓存收益不能以回答质量、工具权限和数据隐私为代价。
