## 一、方案概述：30 秒读完

我们要解决的问题是：

> 用户在 Thread A 的一段 AI 回复上划选文字，输入问题并创建 Thread B 后，B 中既要清楚展示“引用了什么”，还要支持点击引用跳回 A 的原消息、滚动到原位置并高亮；同时，这段引用不能被提前塞进 System Prompt，破坏 A 与 B 之间本来可以复用的缓存。

推荐方案是：

```text
Thread B 的第一条用户消息 B1
├── 引用卡片：划选的原文 + 来源信息
└── 用户问题：用户在弹窗里输入的内容
```

其中：

- **模型只看到引用原文和用户问题**；
- **产品界面额外看到来源 Thread、来源 Message 和文字位置线索**；
- **来源信息由服务端根据已经验证的分支关系生成，不能完全相信客户端传入的数据**；
- **Thread 本身仍保存分支来源，B1 中的引用则是一份可展示、可点击、可扩展的引用快照**。

本次推荐的核心结论只有四条：

1. **引用应该进入 B1，而不是进入包含具体原文的 System Prompt。**
2. **引用不应只是一个字符串，而应是一块结构化的消息内容。**
3. **跳转和高亮所需的来源信息应持久化，但不发送给模型。**
4. **现有代码已经具备大部分基础，主要缺口是把这些能力接成一条完整链路。**

---

## 二、目标理解

### 用户目标

用户看到 Thread B 中的引用时，能立即理解这个分支在讨论 A 中的哪一段；需要核对上下文时，可以点击回到原文，而不是手动寻找来源。

### 工程目标

系统需要让一条用户消息同时具备：

- 可展示的引用正文；
- 可验证的来源身份；
- 可恢复的文字位置；
- 只向模型暴露必要内容的转换规则；
- 不破坏分叉前共同历史缓存的排列顺序。

### 成功标准

1. Thread B 的第一条用户消息可以同时展示引用和用户问题。
2. 点击引用后，可以打开来源 Thread，定位来源 Message，并尽可能高亮当时划选的文字。
3. 来源 Message 后来被替换时，系统仍能说明“这是历史回复中的引用”，不能悄悄跳到另一条新回复。
4. 模型请求中，A 的共同历史排在 B1 引用和问题之前；内部 Thread ID、Message ID 和位置数据不进入模型输入。
5. 编辑、重试、刷新和先建空分支后再提问，不会丢失引用。

以上目标已经通过前几轮讨论完成方向确认，因此本次直接进入完整调研，不再重复设置中途等待点。

## 三、这项能力为什么有必要

### 1. 只保留顶部“讨论焦点”还不够

当前分支列顶部已经能够展示被划选的文字。这能说明 Thread B 的来源，但存在三个限制：

- 用户消息 B1 本身不是一条完整、可独立理解的消息；
- 以后把 B1 展示到搜索结果、消息列表或分享页面时，必须额外找到 Thread 才知道它引用了什么；
- 以后实现 `@Thread`、一条消息引用多个来源时，单个 Thread 的分支字段不够用。

### 2. 只把引用和问题拼成普通字符串也不够

例如：

```text
引用：Prompt Cache 只能复用相同前缀

问题：为什么必须是相同前缀？
```

它看起来简单，但系统以后很难可靠地区分：

- 哪部分是引用；
- 哪部分可以编辑；
- 点击哪里跳转；
- 引用来自哪条消息；
- 一条消息是否包含多个引用。

如果以后还要从这段字符串里重新解析结构，维护成本反而更高。

### 3. 外部服务不能替代这项能力

这是 Thread Chat 自身的领域语义，涉及项目内权限、Message 身份、分支快照、历史版本和页面导航。通用 SaaS 或缓存服务无法理解这些关系，因此不能通过购买外部服务直接解决。

结论是：

> 这项能力需要修改应用自身的消息和导航流程，但可以大量复用项目现有模块，不需要从零建设。

## 四、当前代码已经做到了什么

用户现在的操作链路可以简化为：

```text
在 A 的 AI 回复中划选文字
        ↓
前端记录文字、来源 Thread、来源 Message 和文字位置
        ↓
用户在弹窗输入问题
        ↓
服务端创建 Thread B
        ↓
Thread B 保存分支来源和文字位置
        ↓
B1 目前只保存用户输入的问题
```

### 已有能力一：划选时已经拿到了完整来源

`app/thread-chat/branching/selection/use-assistant-text-selection.ts` 中的 `SelectionInfo` 已经包含：

- 划选文字；
- 来源 Thread ID；
- 来源 Message ID；
- 用于弹窗定位的临时屏幕位置；
- 可持久化的文字锚点。

其中临时屏幕位置只适合当下显示弹窗，不适合长期保存；文字锚点才是未来回跳和高亮的关键。

### 已有能力二：已经有一套较可靠的文字锚点

`lib/thread-chat/domain/text-anchor.ts` 已经定义：

```text
准确原文
原文前面的短文本
原文后面的短文本
可选的起止字符位置
```

这与 W3C Web Annotation 的 `TextQuoteSelector` 和 `TextPositionSelector` 思路一致：

- 字符位置用于内容没变时快速找到；
- 准确原文和前后文用于内容排版变化、重复文字时重新定位。

这比保存 DOM 路径、屏幕坐标或滚动距离可靠得多。

### 已有能力三：Thread 已经保存分支来源

`lib/thread-chat/application/fork-thread.ts` 创建子 Thread 时已经保存：

- 父 Thread；
- 来源 Message；
- 冻结的继承历史；
- 划选原文；
- 文字锚点。

服务端还会验证来源 Message 存在，并检查锚点中的准确原文与划选原文一致。

### 已有能力四：消息协议已经预留引用内容

`lib/thread-chat/contracts/ui-message.ts` 已经定义 `quote` 类型的数据块，当前内容为：

```text
引用文字 text
```

前端 `app/thread-chat/core/projections.ts` 和用户消息组件也已经能识别并展示这种引用。

### 已有能力五：模型上下文已经知道如何读取引用

`lib/thread-chat/application/compile-model-context.ts` 会把 `data-quote` 转换成模型可以理解的文本，同时可以忽略其他产品内部数据。

这意味着产品可以在同一引用块中保存来源 ID 和文字锚点，但只把引用正文发给模型。

### 当前最大缺口

B1 创建时仍然只调用普通的 `buildUserParts(text, files)`，没有把 Thread 的引用信息写入 B1；与此同时，具体 `anchorText` 仍由 `lib/chat/thread-chat-prompt.ts` 拼进 System Prompt。

因此当前状态是：

```text
Thread 层已经知道来源
消息协议已经支持引用
UI 已经支持展示引用
模型转换已经支持引用
但创建 B1 时没有真正把它们连接起来
```

| 目标能力 | 现状 | 差距 | 风险等级 |
|---|---|---|---|

| 未来支持多个引用和 `@Thread` | `data-quote` 可扩展 | Thread 只有一个父来源，消息引用还没有通用来源模型 | 中 |

## 六、需要研究的能力模块

### 可直接复用

1. **划选信息采集**：已经能获得来源和文字锚点。
2. **Thread 分支关系**：已经保存父子关系、来源 Message 和冻结历史。
3. **文字重新定位**：已有位置、准确文本和模糊匹配策略。
4. **消息持久化**：Messages 已以 Parts 形式保存，不需要为了引用另建一张表。
5. **模型转换**：可以只把选定的数据块转成模型文本。

### 可扩展

1. **引用数据块**：从只有 `text` 扩展为“正文 + 来源”。
2. **B1 创建流程**：服务端把经过验证的 Thread 来源写入第一条用户消息。
3. **用户消息 UI**：引用卡片增加点击、来源状态和回跳反馈。
4. **编辑与重试**：编辑问题时保留不可编辑的引用快照。
5. **模型提示规则**：System Prompt 只保留稳定的“如何理解引用”规则，不再包含具体原文。

### 当前缺失

1. **来源解析结果**：来源正常、来源是历史版本、来源不存在等状态。
2. **回跳后的聚焦行为**：滚动、短暂高亮、失败提示。
3. **引用完整性测试**：刷新、编辑、重试和空分支路径的回归验证。
4. **缓存前缀对比测试**：确认移动引用后，A 的共同历史保持一致。

## 七、候选方案对比

### 方案 A：继续只在 Thread 上保存引用

做法：保持当前模式，B1 仍只有问题，引用继续显示在分支顶部。

| 维度 | 评价 |
|---|---|
| 当前分支展示 | 可以满足 |
| 点击回跳 | 可以通过 Thread 字段实现 |
| B1 独立可读性 | 较差 |
| 多引用和 `@Thread` | 不适合 |
| 缓存 | 如果具体引用继续进入 System Prompt，仍不理想 |
| 改造成本 | 最低 |

**判断：不推荐作为长期方向。** 适合只做最小回跳，但无法形成通用的引用消息能力。

### 方案 B：把引用和问题拼成一段普通文本

做法：B1 保存为“引用：……\n问题：……”。

| 维度 | 评价 |
|---|---|
| 开发速度 | 快 |
| 模型理解 | 基本可用 |
| 引用样式 | 需要重新解析文本 |
| 点击回跳 | 缺少稳定来源 |
| 编辑 | 容易误改引用 |
| 多引用 | 容易变得混乱 |

**判断：不推荐。** 它省掉的是最初的一点结构设计，却会把复杂度转移到所有后续功能中。

### 方案 C：B1 使用结构化引用块，来源由服务端补全

做法：B1 同时包含：

```text
引用块
用户问题文本
```

引用块保存：

- 被引用的文字；
- 来源 Thread；
- 来源 Message；
- 文字锚点；
- 格式版本。

模型转换时只输出引用文字，不输出内部 ID 和锚点。

| 维度 | 评价 |
|---|---|
| 产品体验 | 最完整 |
| 缓存 | 引用可以放在共同历史之后 |
| 点击回跳 | 有完整来源 |
| 编辑 | 可以只编辑问题 |
| 未来扩展 | 可支持多个引用、`@Thread`、引用文件段落 |
| 改造成本 | 中等，现有模块大多可复用 |

**判断：推荐。** 它最符合现有 Parts 消息模型，也能同时解决产品体验和缓存问题。

### 方案 D：立即新建独立 Reference 实体或数据库表

做法：引用不直接保存在 Message Parts，而是新建 Reference 记录，消息只保存 Reference ID。

| 维度 | 评价 |
|---|---|
| 复杂引用治理 | 最强 |
| 当前单一分支引用 | 明显过度 |
| 查询与事务 | 更复杂 |
| 删除和权限 | 需要新增完整规则 |
| 后续跨 Project 引用 | 有价值 |

**判断：暂不推荐。** 当产品真正出现跨 Project、多用户共享、大量引用复用时再评估。当前可以把结构化引用块当作未来独立实体的前置模型。

## 八、推荐方案的核心机制

### 1. B1 是一条消息，但内部有两种内容

用户看到：

```text
┌ 引用 ──────────────────────────┐
│ Prompt Cache 只能复用相同前缀  │
│ 来自主线 · 点击查看原文         │
└───────────────────────────────┘

为什么必须是相同前缀？
```

系统保存的逻辑则是：

```text
B1
├── 引用内容块
└── 普通问题文本
```

这两块处于同一条用户消息中，但用途不同：

- 引用块不可随着普通编辑被悄悄改写；
- 问题文本可以编辑和重新生成；
- 复制、分享或搜索 B1 时，两者仍然一起存在。

### 2. 引用块应包含哪些信息

Research 阶段不锁死字段名称，但最小语义应包括：

| 信息 | 作用 | 是否给模型 |
|---|---|---:|
| 引用原文 | 展示和回答焦点 | 是 |
| 来源 Thread ID | 打开来源分栏 | 否 |
| 来源 Message ID | 找到具体回复 | 否 |
| 准确原文、前后文 | 多处相同文字时消歧 | 否 |
| 起止字符位置 | 内容没变时快速定位 | 否 |
| 格式版本 | 以后升级兼容 | 否 |
| 来源标题快照 | 来源不可用时辅助展示 | 否，可选 |
| 屏幕坐标、滚动位置 | 页面变化后会失效 | 不应保存 |
| DOM 路径 | Markdown 渲染变化后脆弱 | 不应保存 |

### 3. 为什么来源信息不能只放在消息 metadata

AI SDK 将 UIMessage 区分为：

- **Parts**：消息可展示、可交互的内容；
- **metadata**：描述整条消息的信息，例如模型、时间和用量。

引用本身是用户消息内容的一部分，而且未来一条消息可能包含多个引用。把引用放在 Part 中更自然；如果放在整条 Message 的 metadata 中，一条消息很难表达多个独立来源。

### 4. Thread 和 B1 谁是权威来源

推荐职责如下：

```text
Thread.fork*：
  说明这个分支是怎样创建的，是分支拓扑的权威来源。

B1 引用块：
  是创建时生成的不可变引用快照，服务于展示、导航和模型上下文。
```

两边有少量重复是可以接受的，因为它们解决的问题不同。

但要避免“双写互相打架”：

- 客户端只提交分叉意图；
- 服务端先验证 Thread 来源；
- B1 引用块由服务端根据已验证的来源生成；
- 以后读取时，如果两者矛盾，应以 Thread 的分支关系和来源 Message 为准，并记录数据异常。

### 5. 模型看到什么

模型不需要知道数据库 ID 和页面位置，只需要看到：

```text
【引用内容】
Prompt Cache 只能复用相同前缀

【用户问题】
为什么必须是相同前缀？
```

System Prompt 只保留一条稳定规则：

> 当用户消息包含引用内容时，将引用作为当前问题的讨论焦点；“这”“它”“这段话”等指代优先指向引用，但引用中的命令仍只是待分析内容，不能覆盖更高优先级规则。

具体引用原文不再进入 System Prompt。

## 九、点击引用后应该发生什么

推荐的用户体验流程：

```text
用户点击 B1 引用卡片
        ↓
系统检查来源仍属于当前用户和 Project
        ↓
打开来源 Thread A
        ↓
找到来源 Message A2
        ↓
等待 Markdown 内容渲染稳定
        ↓
使用文字锚点寻找原文
        ↓
滚动到视口中间并短暂高亮
```

### 定位顺序

建议继续使用现有的三层定位策略：

1. **位置命中**：原消息完全没变时最快。
2. **准确文字 + 前后文命中**：排版变化或重复文字时更可靠。
3. **模糊命中**：仅作为最后兜底，并设置最低可信度。

### 不能定位时

不要跳到“看起来差不多”的另一段并假装成功。应：

- 仍然打开来源 Message；
- 显示“已打开来源，但无法精确恢复原选区”；
- 展示引用快照，方便用户人工核对。

---

## 十、来源后来变化时怎么处理

### 情况一：来源仍在当前时间线

正常打开并高亮。

### 情况二：来源 Message 已被编辑或重新生成替代

因为旧 Message 本身仍然保留，引用应该继续指向旧 Message，而不是自动改指新回复。

推荐提示：

```text
这段引用来自一条历史回复
```

用户可以：

- 查看当时的原始回复和高亮位置；
- 再选择查看当前版本。

不能静默跳到替代后的 Message，因为新回复即使有相似文字，语义也可能不同。

### 情况三：来源 Thread 已归档

允许只读打开，并标明已归档。

### 情况四：来源已被删除或无权限

只显示当时保存的引用快照，并说明来源不可访问。不能暴露其他用户或其他 Project 的信息。

在当前同一 Project 分支模型中，级联删除通常会让目标和引用一起消失；但未来支持跨 Thread、跨 Project 引用后，这个状态会变得重要，因此应在消息引用语义中提前保留。

## 十一、对缓存的影响

### 当前不理想的排列

当前具体 `anchorText` 会被拼进 System Prompt，整体近似为：

```text
固定工具
固定规则
Thread B 的具体引用文字
A 的共同历史
B1 的问题
```

不同分支的引用文字不同，所以请求在进入 A 的共同历史以前就已经发生变化。

### 推荐排列

改为：

```text
固定工具
固定 System Prompt
A 的共同历史
B1 的引用块
B1 的问题
```

从同一个 A 创建 B、C 两个分支时：

```text
Thread B：固定部分 + A 的历史 + 引用 B + 问题 B
Thread C：固定部分 + A 的历史 + 引用 C + 问题 C
```

两次请求直到 A 的共同历史结束以前都可以保持一致。

### 来源信息会不会破坏缓存

不会，前提是模型转换只输出引用原文。

```text
产品内部保存：
来源 Thread、来源 Message、文字锚点

发送给模型：
引用正文
```

这些内部信息位于产品数据库和 UIMessage 中，不进入模型输入，因此不会增加模型 Token，也不会改变共同前缀。

### 仍需接受的边界

即使排列正确，也只能说“具备最大程度复用条件”，不能保证每次都命中。实际结果还取决于：

- 是否使用同一个模型；
- 工具定义是否相同；
- 请求是否走到相同上游线路；
- 缓存是否过期；
- 共同内容是否达到服务商的最小长度；
- A 的最后一条 AI 回复此前是否已经作为下一次请求输入出现过。

因此需要通过缓存读取量和首次响应时间验证，不能只靠请求结构推断。

## 十二、编辑、重试和空分支的规则

### 编辑 B1

用户只能编辑问题文本，引用块默认不可编辑。

编辑前：

```text
引用：相同前缀
问题：为什么？
```

编辑后：

```text
引用：相同前缀
问题：请用一个生活例子说明。
```

引用仍指向同一来源和同一选区。

### 重试回答

重试只新建 Assistant Message，不改变 B1 引用。

### 编辑并重新生成

新 User Message 应继承原 B1 的引用块，只替换问题文本。否则新生成回答会突然失去分支焦点。

### 先创建空分支，稍后第一次提问

第一次真正发送用户消息时，服务端应自动把 Thread 的来源写入引用块。不能依赖前端再次提交原始引用，否则刷新或换设备后可能丢失。

### 后续 B2、B3

默认不重复附加引用块，因为 Thread 的焦点已经建立；后续用户可以继续普通对话。

只有用户主动再次引用其他内容时，新的用户消息才增加新的引用块。

## 十三、核心风险与偏差预期

| 风险点 | 可能的偏差 | 影响范围 | 发现方式 | 纠偏路径 |
|---|---|---|---|---|
| Markdown 渲染文本与原始模型文本不完全一致 | 服务端难以再次验证选区是否真的存在 | 引用可信度、跳转 | 对代码块、列表、链接做定位实验 | 约定统一的可见文本规范，服务端验证 ID，客户端负责 DOM 定位 |
| 来源 Message 已被替代 | UI 只展示当前版本，找不到旧回复 | 历史引用 | 构造 edit/regenerate 场景 | 提供历史来源只读视图，不自动改指新回复 |
| 编辑 B1 时重建纯文本 Parts | 引用悄悄丢失 | 分支语义、缓存 | 编辑后刷新测试 | 编辑命令显式继承不可变引用块 |
| 空分支路径没有 Quote | 两种创建路径行为不一致 | 产品一致性 | 对比带问分叉和空分支后首问 | 由服务端识别第一条用户消息并补全 |
| 客户端伪造来源 ID | 可能跳到错误内容或越权 | 安全 | 权限与篡改测试 | 来源全部经 owner/project 校验，服务端生成最终引用块 |
| 模型看到内部 ID 和锚点 | 浪费 Token，可能泄露内部结构 | 成本、隐私 | Prompt 快照测试 | `convertDataPart` 只输出引用正文 |
| 模糊匹配误高亮 | 用户被带到错误位置 | 信任体验 | 重复文本和低相似度测试 | 低可信度不高亮，只打开来源并说明 |
| 引用数据重复于 Thread 字段 | 后续更新出现不一致 | 数据维护 | 构造冲突数据测试 | 明确 Thread 为分支关系权威，Quote 为创建时快照 |
| 第一版结构过度绑定“分支” | 以后 `@Thread` 再次重做 | 扩展成本 | Spec 评审 | 数据块命名和语义保持通用，首个使用场景只实现分支来源 |

## 十四、核心风险验证计划

Research 阶段不实现完整功能，但建议进入 Spec 前后完成以下最小实验。

### 实验一：引用能否稳定持久化

**问题：** `data-quote` 增加来源和文字锚点后，能否经过数据库保存、刷新加载和 UI 映射而不丢字段？

**假设：** 当前 Messages 已保存完整 Parts，可以直接承载。

**方法：** 构造一条包含引用块的用户消息，经过写入、读取、前端映射和再次保存。

**通过标准：** 引用正文、来源 ID 和锚点完全一致；模型转换只得到引用正文。

### 实验二：回跳和高亮是否可靠

**问题：** 在普通段落、重复文字、列表、代码块和 Markdown 链接中，现有文字锚点能否恢复选区？

**假设：** 位置 + 准确原文/前后文可以覆盖主要场景，模糊定位只需做兜底。

**方法：** 建立一组固定 Markdown 样例，保存锚点后重新渲染并定位。

**通过标准：** 常见内容准确定位；无法可信定位时不误高亮。

### 实验三：编辑和空分支是否保持引用

**问题：** B1 编辑、重新生成，以及空分支后的第一次提问，会不会丢失引用？

**假设：** 只要引用由服务端生成，并在编辑时从原消息继承，就能保持一致。

**通过标准：** 所有路径的第一条有效用户消息都拥有同一来源快照。

### 实验四：共同历史缓存是否真的改善

**问题：** 移动引用以后，兄弟分支在 A 历史结束以前是否形成相同模型输入？

**方法：** 对两个兄弟分支生成模型请求快照，比较最前面的工具、System 和 A 历史，并记录服务商返回的缓存读取量。

**通过标准：** B、C 的输入只从各自引用块开始出现差异；支持缓存的线路出现可解释的读取数据或首次响应改善。

### 实验五：来源权限和篡改

**问题：** 客户端修改来源 Thread、Message 或锚点后，是否可能引用无权访问的内容？

**通过标准：** 服务端拒绝跨用户、跨 Project 或与真实分支来源不一致的数据；最终持久化引用只能来自服务端验证结果。

## 十六、调研后仍未完全解决的不确定性

### 1. “可见文字”的统一定义

浏览器中划选的是 Markdown 渲染后的文字，而服务端持有的是 UIMessage Parts。代码块、链接、表格和工具插卡可能让两者不完全一致。

这个问题不会推翻推荐方向，但需要在 Spec 阶段明确：

- 锚点基于哪一份规范化文本；
- 服务端验证到什么程度；
- 客户端定位失败时如何安全降级。

### 2. 历史 Message 的产品呈现

数据层能够保留被替代的 Message，但当前工作台主要展示有效时间线。回跳历史引用需要一个用户可理解的入口。

这是产品交互决策，不应由底层定位算法自行决定。

### 3. 跨 Project 引用

当前研究只覆盖同一 Project 内的分支来源。跨 Project 会额外涉及权限、删除、分享和来源失效，不应顺手并入第一版。

### 4. 多模态引用

当前锚点是文本锚点。未来引用图片区域、PDF 页码或 Artifact 段落，需要新的 selector，但可以继续沿用“引用正文/预览 + 来源 + 定位器”的总体模型。

## 十七、下一步建议

建议进入 Spec 阶段时按以下顺序细化：

### P0：定义引用语义和权威来源

明确：

- Quote 是用户消息内容，不是 Message metadata；
- Thread 保存分支关系；
- Quote 是服务端生成的引用快照；
- 模型只看到引用正文；
- 客户端不能自行决定最终来源。

### P1：定义完整生命周期

覆盖：

- 带问题创建分支；
- 空分支后的第一次提问；
- 编辑 B1；
- 重新生成；
- 刷新恢复；
- 来源成为历史版本；
- 来源不可访问。

### P2：定义回跳和高亮体验

明确打开列、等待渲染、定位顺序、滚动、高亮时长和失败提示。

### P3：定义模型输入和缓存验收

明确：

```text
固定 System
A 的共同历史
B1 引用正文
B1 用户问题
```

并通过请求快照和真实缓存 usage 验证。

### P4：为未来引用能力预留边界

数据语义不要限制为“只能引用父 Thread”，但第一版只实现分支首条消息，避免把 `@Thread`、跨 Project 和多模态引用一起做大。

## 十八、最终结论

一句话总结：

> **让 B1 成为一条真正完整的引用式用户消息：引用原文和问题属于消息内容，来源 Thread、来源 Message 和文字锚点属于产品导航信息；两者一起持久化，但只有引用原文和问题进入模型。**

这条方案成立的主要依据是：

1. 当前代码已经采集来源 ID 和文字锚点；
2. Thread 已经保存并验证分支来源；
3. UIMessage 已经支持自定义数据块；
4. 用户消息 UI 和模型转换已经识别 `data-quote`；
5. 现有高亮实现已经证明文字锚点可以用于重新定位；
6. 把引用移动到 B1，可以让 A 的共同历史留在变化内容之前，更符合 Prompt Cache 的共同前缀要求。

因此，这不是一次从零重做，而是把已经存在但分散的能力收拢成一个清晰的“引用消息”领域能力。
