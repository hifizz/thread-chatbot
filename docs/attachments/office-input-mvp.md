# 办公文件输入 MVP（#82）

基于 main `7da00eaba9fb116a4ff4612b08005f51e886cd45`。本 PR 是 #82 的办公文件切片，不关闭整个跟踪 Issue。

## 交付范围

| 文件 | 本轮处理 | 边界 |
| --- | --- | --- |
| PDF | 接通 Thread Composer；沿用现有按页文本提取与 PDF 检索 | 无文本层的扫描件明确失败；不新增视觉理解 |
| DOCX | 段落、表格、脚注、页眉/页脚文本 | 不承诺版式复原或图片理解；段落编号不冒充页码 |
| XLSX | 多工作表、单元格地址、原始值、数字格式、日期、公式及缓存值、合并单元格标记 | 不执行公式；缓存可能过期；包含并标记隐藏工作表 |
| CSV | UTF-8（含 BOM）、引号、逗号、单元格内换行、空值、前导零 | 非 UTF-8 明确提示另存；默认逗号分隔；行号指记录号 |
| PPTX | 按真实演示顺序提取正文、表格、对应备注 | 不识别图片/图表视觉；保留空页序号 |
| DOC/XLS/PPT、ZIP、视频、其他 | Thread Composer 给出支持范围和另存提示 | 不伪装为可读取文件 |

仍要求输入问题文本；上传重试、草稿恢复、孤立对象清理不在这次切片中。

## 数据与链路

沿用 `create → R2 PUT → ingest → ready → 消息稳定 file 引用`。原文件保存在 R2；客户端 MIME 规范化兼容浏览器空 MIME 和 CSV 被报告为 Excel，ingest 校验真实文档结构。

无需新增实体或数据库迁移。`attachments.pages: string[]` 保存提取片段：PDF 仍按物理页；Office 片段自身携带段落/幻灯片/工作表和单元格位置。`pageCount` 仅用于 PDF，Office 为 null。不是把 Office 伪装成 PDF。解析只在 ingest 做一次，后续预览和对话读保存的片段。

客户端与服务端共享 `THREAD_ATTACHMENT_MIME_TYPES`。发送前继续校验登录、所有权、ready 状态及 MIME 一致性。Office 转为文本，不依赖模型视觉能力；图片维持原有视觉能力门禁。

本轮提取库：OfficeParser 7.8（Word/PPT 结构）、ExcelJS 4.4（单元格类型/公式）、csv-parse 6.1（CSV）、yauzl（受限 ZIP 校验）、xmldom（PPT 顺序及备注关系）。OfficeParser 按内部文件编号归并 PPT 的行为由 `presentation-order.ts` 按真实关系校正，并有打乱编号的文件回归测试。

文件上限 20MB，实际解压上限 64MB、4,000 部件；最多保存 100 万字符和 10,000 片段，表格最多 20 万单元格。超限或解析失败显示错误，保留输入供用户移除/重新上传；禁止把解析失败标为 ready。ZIP 不落盘、不执行宏或外部链接，XML 自定义实体被拒绝。

## 模型上下文与阅读体验

使用现有统一附件预算。Office 按保存的确定性顺序提供正文；超预算明确标记只提供部分内容，不声称已读全文、不得从局部计算全表统计。模型请求不再解析原始 Office 二进制。原消息保持稳定引用，转换只用于当前模型输入。

文件卡片展示上传/解析状态，点击打开鉴权的同源“已提取内容”预览，可下载原始文件。明确说明图片、图表未识别。不会将 Office 转换生成的 HTML 放进页面执行。

## 官方 API 支持核实（2026-09-06）

- [OpenAI File inputs](https://developers.openai.com/api/docs/guides/file-inputs)：Responses 的 input_file 支持 PDF、DOC/DOCX、PPT/PPTX、CSV/XLS/XLSX。PDF 可包含文本和页面图像；非 PDF 文档主要提取文字；表格有专门处理。这不能推导所有 Chat Completions 兼容中转端点都支持相同能力。
- [Claude Files API](https://platform.claude.com/docs/en/build-with-claude/files)：document block 支持 PDF/纯文本；DOCX/XLSX 需转换为文本/PDF，或上传给 code execution 的 container_upload。Files API 能存文件，不等于 document block 能直接理解该文件。

因此本轮采用所有文本模型可用的提取路径。后续原生 PDF/Office 必须按供应商端点实测后开启，不能根据模型名称自动放行。本次不宣称已完成真实付费模型效果验证。

## 迭代顺序

1. 可用（本轮）：文件能上传、解析、预览、进入模型上下文；常见结构不会默默丢失，错误能理解。
2. 能用：建立代表性用户样本评测；大表按问题选择区域与完整计算工具；扫描 PDF/OCR；按实际供应商验证原生输入。
3. 好用：文档原貌预览、定位引用、页面视觉理解、进度细化、上传原地重试、草稿与清理生命周期。

## 验收

自动测试：`node --import tsx e2e/attachments/office-attachment.test.mjs`。

手动验收（需要配置数据库、R2 和模型）：

1. 上传 DOCX 和 CSV，看到“正在解析文件”后就绪；输入“分别总结文件内容”发送，确认回答能引用实际内容。
2. 上传 XLSX，询问指定工作表 B3 的公式与缓存结果；确认日期、百分比格式、编号前导零、空值不会混淆。
3. 上传调整过页序、备注编号不一致的 PPTX，询问第 1 页备注；答案应对应当前演示页序。
4. 点击发送后的文件卡片，对照提取内容并下载原文件；刷新、编辑、重试与分叉后引用仍可读取。
5. 文本型 PDF 成功；扫描件、损坏/加密 Office、错误 CSV 编码明确失败且不能发送。更换文本模型仍能读取 Office，图片维持原有门禁。
6. 大文件超出上下文预算时，回答应承认片段范围；超出解析上限时上传阶段明确失败。
