## Context

现有状态把所有对话节点表示为 `Thread`，并作为单行 JSON 状态持久化。标题生成仅在 ForkedThread 首轮问答完成后触发；MainThread 的树标题仍从首条用户消息派生并截断。

## Goals / Non-Goals

**Goals:**

- 在首条 MainThread 用户消息发送后异步生成一次语义标题，不等待或影响主回答。
- 将 MainThread 成功生成的完整标题用于树记录和各处默认展示，同时保留可靠回退。
- 以 `title-generation` 作为统一标题能力，并复用单次尝试和标签页级防重复保障。

**Non-Goals:**

- 不为历史会话批量补生成标题。
- 不自动重试失败标题，也不覆盖用户手动重命名。
- 不改变 Thread 的持久化模型、整树 schema 或对话生成管线。

## Decisions

### 不在本变更中改变 Thread 持久化模型

本变更沿用现有 `ThreadTreeState` 与 schema v2，不增加 `Thread.kind` 或其他领域角色字段，也不改变 `Thread.id` 的表示。标题候选使用现有树结构识别 MainThread 与 ForkedThread：主线使用首条用户消息，非根 Thread 使用 Fork 上下文。

将 Thread 与 Message 规范化为服务端一等实体、调整其 ID 与并发模型，是独立的持久化架构专题，记录在 GitHub Issue #34；不得作为本次标题功能的附带改动。

### 使用无兼容层的统一标题接口

`/api/title` 接受 MainThread 或 ForkedThread 的显式上下文。MainThread 使用首条用户消息；ForkedThread 使用锚点、首问和首答摘录。两类请求共享模型、输出清洗和单次调用策略。旧 `/api/branch-title`、`/api/thread-title`、缺省请求类型和旧浏览器存储键均不保留。

备选方案是保留旧端点或缺省请求体的转发。当前没有旧客户端或历史状态需要支持，这只会增加术语和测试负担，因此不采用。

### 在标题 hook 中按现有树结构触发

标题 hook 同时识别两类候选：MainThread 取首条用户消息并在发送后立即触发；ForkedThread 继续等待首答可渲染。两者都先原子持久化“已尝试”标记，再发起请求。成功生成状态与“已尝试”分离，使 MainThread 失败时保留派生回退标题。

### 保持用户重命名优先

自动标题只更新树记录的机器标题与线程状态，不写用户自定义标题字段。读取和主线列头继续以用户自定义标题优先，确保异步返回不会覆盖显式用户选择。

## Risks / Trade-offs

- [标题请求在首答前失败] → 主线保持现有派生标题，对话不受影响且不自动重试。
- [首条消息刚提交即刷新] → 在标签页保存尝试标记，并将尝试状态纳入整树持久化。
- [模型标题返回较慢] → 初始展示沿用派生标题；结果仅替换标题，不影响消息流。
- [既有树无标题状态] → 缺省值解释为未自动生成，保留原有派生标题行为。

## Migration Plan

1. 发布标题生成逻辑，不改变整树状态 schema。
2. 新会话从首条消息开始使用自动标题；既有会话维持当前派生标题，直到后续创建或修改。
3. 如需回滚，停止新的标题请求；主线仍可回退到首条消息派生标题。
