# Research 质量自检

交付调研结论前逐项检查。发现任一关键项不满足时，应补充证据、降低结论置信度或明确标记为待验证，而不是用更肯定的措辞掩盖缺口。

| 维度 | 检查问题 |
|---|---|
| 目标清晰度 | 读者能否用一句话说出要做什么、为什么做？Why、What 与成功标准是否已由用户确认？ |
| 检查点遵循 | 是否经过目标确认和计划确认？最终是否停在结论确认，而非自动进入 Spec/Implement？ |
| 可判断性 | 工程师读完每个模块后，能否判断推荐是否合理？核心机制、假设和 trade-off 是否显式？ |
| 基线准确性 | 对当前项目能力的描述是否有代码、文档或实验依据？事实、推断与未知是否分开？ |
| 范围纪律 | 是否只覆盖核心路径和用户强调的重点？是否把接口、表结构或逐文件实现错误地提前到 Research？ |
| 深度恰当性 | 高风险问题是否得到验证或被明确列为待验证？低风险问题是否避免过度展开？ |
| 复用优先 | 是否实际评估了可复用方案，而不是默认自研？没有选择候选方案的原因是否公平、具体？ |
| 决策有据 | 每项推荐能否追溯到来源、代码事实、实验结果或明确推理？是否存在无依据的“显然”“一定”？ |
| 不确定性透明 | 是否明确列出已验证、假设、未知三类信息？置信度是否与证据强度一致？ |
| 风险可纠偏 | 是否说明风险如何被发现、影响范围和纠偏路径？ |
| 工程师介入 | 后续 Spec/Implement 中需要用户或工程师拍板的节点是否明确？ |
| 表达清晰度 | 是否先讲直觉与结论，再给精确机制和证据？术语是否一致，表格是否真正帮助比较？ |
| 工具纪律 | 是否只在需要外部或最新事实时使用搜索？引用内容是否支持对应结论？ |
| 安全与真实性 | 是否避免伪造实验、来源、代码状态或执行结果？是否未执行 Skill 包脚本或请求越权工具？ |

## 最低交付门槛

最终结论至少必须做到：

1. 目标与成功标准已确认；
2. 推荐方案、关键假设和主要代价可被快速定位；
3. 阻塞性未知被显式列出；
4. 高风险结论有证据或最小验证计划；
5. 下一步只指向 Spec 的起点，不包含未经确认的生产实现承诺。
