# Research 结论交付模板

最终调研结论按以下结构组织。重点是让工程师能够判断方案，而不是堆积资料。

## 一、方案概述

用约 30 秒可读完的篇幅说明：

> 我们要做什么、为什么做、推荐的核心方案、需要新增或引入哪些模块，以及最大的风险是什么。

## 二、目标与成功标准

- 用户目标（Why）
- 工程目标（What）
- 已确认的成功标准
- 明确不在本次范围内的内容

## 三、基线与 Gap

| 目标能力 | 当前现状 | 主要差距 | 风险等级 | 依据 |
|---|---|---|---|---|

事实、推断和未知必须区分；不要把推断写成已经存在的项目能力。

## 四、核心机制与选型

对每个关键模块依次说明：

1. 它解决什么问题；
2. 推荐方案如何工作；
3. 依赖什么假设；
4. 为什么没有选择其他候选；
5. 接受该方案意味着接受什么代价。

需要对比时使用：

| 维度 | 候选 A | 候选 B | 自研 |
|---|---|---|---|
| 功能覆盖 | | | |
| 集成成本 | | | |
| 维护状态 | | | |
| 文档质量 | | | |
| 许可证 | | | |
| 长期风险 | | | |

每个模块最后给出：

- 推荐；
- 理由；
- Trade-off；
- 假设与结论失效条件。

## 五、核心风险验证

每项最小实验使用：

> **实验：名称**
>
> 问题：要消除什么不确定性  
> 假设：预期结果  
> 方法：最小验证方法  
> 判定标准：什么算通过或失败  
> 结果：实际证据  
> 对方案的影响：结论如何改变推荐

没有实际执行实验时，不得伪造结果；应明确标为“待验证”。

## 六、风险与偏差预期

| 风险点 | 可能偏差 | 影响范围 | 发现方式 | 纠偏路径 |
|---|---|---|---|---|

## 七、后续决策点

| 阶段 | 决策点 | 需要判断什么 | 触发条件 |
|---|---|---|---|
| Spec | | | |
| Implement | | | |

## 八、未解决的不确定性

逐项说明：

- 仍然不知道什么；
- 为什么当前无法消除；
- 计划在哪个阶段用什么方式消除；
- 如果它最终转化为问题，会影响哪些模块。

## 九、下一步建议

说明：

- 进入 Spec 的起点；
- Spec 应优先细化的顺序；
- 进入下一阶段前仍需用户确认的方案方向。

结尾必须停在结论确认检查点，不自动开始详细设计或编码。
