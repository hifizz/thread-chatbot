# 任务清单 CLI 设计

## 1. 目标与边界

该工具提供一个最小化、本地持久化的任务清单命令行接口，支持：

- 新增任务；
- 按 `id` 升序列出全部任务；
- 将指定任务标记为完成；
- 将数据保存到程序所在目录的 `todos.json`，使任务在重启后仍可读取。

实现仅使用语言标准库，不引入第三方依赖。任务不支持删除、编辑、筛选或多用户并发协作；这些能力不在本次范围内。

## 2. 数据模型与持久化

### 2.1 内存模型

每个任务使用如下字段：

| 字段 | 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| `id` | 正整数 | 唯一、不可变 | 任务标识，用于排序和完成操作 |
| `title` | 非空字符串 | 去除首尾空白后不能为空 | 用户输入的任务标题 |
| `completed` | 布尔值 | 必须为 `true` 或 `false` | 是否已完成 |

新增任务时由程序分配 `id`：读取现有任务中的最大 `id` 后加一；空列表的首个 ID 为 `1`。任务一经创建，不因排序或完成操作而改变 ID。这样即使历史数据的 ID 不连续，也不会产生重复 ID。

### 2.2 `todos.json` 格式

数据文件位于可执行程序（或项目入口脚本）同目录，文件名固定为 `todos.json`。根节点为任务数组，UTF-8 编码，例如：

```json
[
  {
    "id": 1,
    "title": "编写设计文档",
    "completed": false
  },
  {
    "id": 2,
    "title": "执行验收",
    "completed": true
  }
]
```

首次运行时，如果文件不存在，应将任务集合视为空；在首次成功新增任务后创建文件。列出空集合时不必创建数据文件。

读取文件后，程序应校验根节点为数组，且每个对象均包含类型正确的 `id`、`title`、`completed` 字段；同时校验 ID 为正数且不重复、标题有效。发现数据损坏时不得用空数据覆盖原文件。

### 2.3 写入策略

对会变更数据的 `add` 和 `done` 命令，先在内存中完成校验和修改，再将完整数组序列化为 JSON 写回。为降低写入中断造成文件截断的风险，建议：

1. 在与 `todos.json` 相同目录创建临时文件；
2. 写入完整 JSON 并关闭（实现环境支持时执行同步）；
3. 使用原子替换/重命名将临时文件替换为 `todos.json`；
4. 任一步失败时报告错误，保留原数据文件，并尽力清理临时文件。

## 3. 命令格式

以下以可执行命令名 `todo` 表示；实际入口名称变化不影响参数语义。

### 3.1 总览

```text
todo add <标题...>
todo list
todo done <id>
todo help
```

- 参数按 shell 的常规规则解析；含空格的标题可加引号，如 `todo add "购买 牛奶"`。
- `add` 的 `<标题...>` 表示剩余所有参数以单个空格拼接后的标题，因此标题可包含空格。
- 正常完成时进程退出码为 `0`；任何参数、数据或 I/O 失败均使用非零退出码，并向标准错误输出错误信息。

### 3.2 `todo add <标题...>`

新增一个未完成任务。

处理流程：读取现有数据、验证标题、分配下一个 ID、创建 `{id, title, completed: false}`，然后持久化。

成功输出建议采用稳定、便于脚本读取的格式：

```text
Added #3: 购买 牛奶
```

标题只含空白、未提供标题，或标题在去除首尾空白后为空时均为无效输入。

### 3.3 `todo list`

读取所有任务，按数值 `id` 升序输出。即使 JSON 中数组顺序并非 ID 顺序，输出也必须排序；`list` 不修改文件。

每项一行，推荐格式：

```text
[ ] 1 编写设计文档
[x] 2 执行验收
```

其中 `[ ]` 表示未完成，`[x]` 表示已完成。没有任务时退出成功，可不输出任何内容。

### 3.4 `todo done <id>`

将指定 ID 的任务标记为完成，并持久化。`id` 必须是十进制正整数，不能接受 `0`、负数、小数或带非数字字符的值。

- 原本未完成：将 `completed` 设为 `true`，成功后输出 `Completed #<id>: <标题>`。
- 原本已完成：保持其状态不变，仍视为成功（幂等），可输出 `Already completed #<id>: <标题>`。

### 3.5 `todo help`

输出上述用法说明并成功退出。无命令、未知命令以及参数数量不正确均输出简要用法到标准错误并以非零退出。

## 4. 错误处理

错误信息应简洁、具体，并使用标准错误；不得将堆栈、解析器内部细节或部分成功状态当作正常输出。建议按以下类别处理：

| 场景 | 行为 | 示例错误信息 |
| --- | --- | --- |
| 未提供命令、未知命令或参数不匹配 | 不读写数据，输出用法，非零退出 | `错误：未知命令 "remove"。使用 todo help 查看用法。` |
| `add` 标题缺失或为空白 | 不写入数据，非零退出 | `错误：任务标题不能为空。` |
| `done` ID 格式非法 | 不读取或修改任务，非零退出 | `错误：id 必须是正整数。` |
| `done` 的 ID 不存在 | 不写入数据，非零退出 | `错误：未找到任务 #42。` |
| `todos.json` 不存在 | 作为空列表继续执行 | 不输出错误 |
| JSON 无法解析、根节点或字段不合法、ID 重复 | 拒绝执行，绝不覆盖原文件，非零退出 | `错误：无法读取 todos.json：数据格式无效。` |
| 数据文件无法读取（权限、目录错误等） | 不继续使用猜测数据，非零退出 | `错误：无法读取 todos.json：权限被拒绝。` |
| 数据文件或临时文件无法写入、替换失败 | 命令失败，尽力保留原文件，非零退出 | `错误：无法保存 todos.json：磁盘空间不足。` |

对于读取或保存失败，面向用户的信息应包含操作对象（`todos.json`）和可理解的系统原因；实现可保留底层错误作为诊断上下文。对 `done` 而言，只有完成持久化后才能报告成功，避免内存中已修改而磁盘未保存时产生误导。

## 5. 验证要点

实现完成后应至少验证以下场景：

1. 在不存在 `todos.json` 的目录执行两次 `add`，确认生成 ID `1`、`2`，且两项初始均未完成；
2. 重启程序后执行 `list`，确认任务仍存在且按 ID 升序显示；
3. 执行 `done 1` 后再次 `list`，确认任务 `1` 显示为完成；重复执行 `done 1`，确认结果幂等；
4. 验证空标题、非法 ID、不存在 ID、未知命令均返回非零且不改变数据；
5. 手工写入损坏 JSON 或字段类型错误，确认命令报错且不会覆盖该文件；
6. 在不可写目录或模拟写入失败的环境执行变更命令，确认返回保存错误且已有数据保持可用。
